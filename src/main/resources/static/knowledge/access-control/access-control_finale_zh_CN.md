# 访问控制漏洞 - 结业总结

恭喜你完成了访问控制漏洞模块的全部关卡！在这个模块中，你亲手实践了三种经典的越权攻击方式。让我们回顾并深入总结。

---

## 学习路径回顾

### 水平越权 — 商家订单中心

**你学到了什么：**
- 后端未校验资源归属时，仅凭订单编号就能查看其他商家的敏感信息
- 订单编号具有可预测的规律（日期 + 5位数字），使遍历攻击成为可能
- 脱敏展示 ≠ 安全，只要解密接口缺乏归属校验，数据就是裸露的

**攻击本质：**
```
同一权限等级的用户 A 访问了用户 B 的数据
问题出在：服务端没有验证"这条数据是否属于当前请求者"
```

**修复方案：**
```java
// 在每次查询时加入归属校验
SELECT * FROM merchant_orders
WHERE order_no = #{orderNo} AND merchant_id = #{currentUserId}
```

### 垂直越权 — 角色提权攻击链

**你学到了什么：**
- 前端 disabled 字段只是"君子协定"，不能作为安全控制
- 后端接口如果不校验"谁在修改什么字段"，任何人都能篡改任何值
- 攻击可以是一条链：先提权（修改角色），再利用新权限执行高权限操作

**攻击本质：**
```
普通用户 → 篡改自身角色为 ADMIN → 获得管理员权限 → 执行管理操作
问题出在：PUT /api/users/{id} 没有校验"当前用户是否有权修改 role 字段"
```

**修复方案：**
```java
// 方案一：敏感字段白名单
public int updateUser(User user, User currentUser) {
    // 非管理员不允许修改 role 字段
    if (!"ADMIN".equals(currentUser.getRole())) {
        user.setRole(null); // 忽略角色修改
    }
    return userRepository.updateUser(user);
}

// 方案二：专用的角色修改接口 + 权限注解
@PreAuthorize("hasRole('ADMIN')")
@PutMapping("/users/{id}/role")
public void updateUserRole(...) { ... }
```

---

### 前端的秘密 — 隐藏接口发现与 IDOR

**你学到了什么：**
- 前端代码是完全公开的，注释、死代码、调试信息都可能泄露后端接口
- 即使页面没有提供操作入口，后端接口依然存在且可被直接调用
- 安全不能依赖"接口没有暴露在 UI 上"这个假设

**攻击本质：**
```
审计前端源码 → 发现被注释的 API 端点 → 直接调用 → 发现无归属校验 → 越权
这是"信息泄露"+"IDOR"的组合攻击
```

**修复方案：**
```
1. 生产环境移除所有调试代码、注释中的接口信息
2. 前端构建时使用代码混淆和 tree-shaking
3. 后端每个接口都必须独立做权限和归属校验
4. 不要假设"用户不知道这个接口存在"
```

## 三种越权模式对比

| | 水平越权 | 垂直越权 | 前端的秘密（IDOR） |
|--|----------|----------|-------------------|
| **攻击目标** | 同级用户的数据 | 更高权限的操作 | 隐藏接口 + 他人数据 |
| **漏洞根因** | 缺少归属校验 | 缺少权限校验 | 接口暴露 + 缺少归属校验 |
| **前置条件** | 知道他人的资源标识 | 知道高权限接口/可修改角色 | 能获取前端源码 |
| **影响程度** | 数据泄露 | 完全接管系统 | 数据泄露 |
| **检测难度** | 中等 | 较低 | 较高 |

## 访问控制安全设计原则

### 1. 最小权限原则
```
每个用户/角色只能访问其工作所必需的最少资源。
不要给予"可能需要"的权限，只给"确实需要"的权限。
```

### 2. 默认拒绝
```
未明确授权的操作一律拒绝。
白名单 > 黑名单。
```

### 3. 服务端是唯一信任边界
```
前端的任何限制（disabled、hidden、JS校验）都可以被绕过。
所有权限判断必须在服务端完成。
客户端只是用户体验的优化，不是安全控制。
```

### 4. 接口级别的独立校验
```
每个 API 端点都应独立验证：
① 用户是否已认证（Authentication）
② 用户是否有权执行此操作（Authorization）
③ 目标资源是否属于该用户（Ownership）
```

### 5. 不可预测的资源标识
| 方式 | 示例 | 是否推荐 |
|------|------|----------|
| 自增 ID | 1, 2, 3 | 不推荐（可遍历） |
| UUID v4 | `a1b2c3d4-e5f6-...` | 推荐 |
| 加密 ID | `Base64(AES(id))` | 推荐 |
| 日期+随机 | `20260501-87231` | 不推荐（规律可猜测） |

## 安全开发检查清单

### 接口开发时
- [ ] 该接口是否需要登录？→ 添加认证校验
- [ ] 该操作是否限定角色？→ 添加角色/权限校验
- [ ] 该资源是否有归属？→ 添加归属校验
- [ ] 请求参数中是否有"不该由用户控制"的字段？→ 使用白名单过滤

### 代码审计时
- [ ] 搜索所有 UPDATE/DELETE 语句，确认 WHERE 条件包含用户标识
- [ ] 检查角色修改、权限变更类接口是否有额外校验
- [ ] 前端代码中是否遗留了后端接口信息

### 测试阶段
- [ ] 用低权限账号重放高权限请求（Burp Suite / AuthMatrix）
- [ ] 用 A 用户的 Token 访问 B 用户的资源
- [ ] 审查前端 JS 中是否包含未使用的 API 端点

## 实战工具推荐

**Burp Suite — Authorize 插件**
```
1. 配置两个权限不同的账号
2. 用高权限账号正常操作，记录所有请求
3. 插件自动用低权限 Token 重放每个请求
4. 对比响应：若低权限也能成功，则存在越权
```

**手动测试思路**
```
1. 登录普通用户，收集自己的资源 ID
2. 登录另一个普通用户，尝试用第一个用户的资源 ID 访问
3. 修改请求中的 role/permission/is_admin 等字段
4. 查看前端 JS 源码，搜索 /api/ 或 fetch( 关键词
```

## 核心结论

> **认证（Authentication）回答的是"你是谁"；**
> **授权（Authorization）回答的是"你能做什么"。**
>
> 登录成功 ≠ 可以为所欲为。每一个接口、每一条数据、每一个操作都需要独立的权限验证。

你在这个模块中体验到的三种攻击，在真实世界中每天都在发生。OWASP Top 10 中，"失效的访问控制"常年位居第一。

掌握了攻击原理，是为了写出更安全的代码。

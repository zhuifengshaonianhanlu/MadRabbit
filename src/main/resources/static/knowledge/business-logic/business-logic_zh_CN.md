# 🧠 实验手册：业务逻辑漏洞

### 0. 序言
WAF 能挡住 SQL 注入，却挡不住"买一送十"。业务逻辑漏洞是最难被扫描器发现的漏洞，因为它们不是技术上的错误，而是逻辑上的疏漏。

*   **业务逻辑漏洞**：应用程序业务流程中的设计或实现缺陷，允许攻击者以非预期方式使用系统。
*   **核心思想**：代码没有 bug，但业务有漏洞。

本章目标：**学会从业务流程中发现可利用的逻辑缺陷。**

---

### 1. 价格篡改

**场景**：电商网站的价格在前端计算或由客户端传递。

**攻击示例**：
```http
# 正常请求
POST /order
{"productId": "123", "quantity": 1, "price": 999}

# 攻击请求 — 篡改价格参数
POST /order
{"productId": "123", "quantity": 1, "price": 0}
```

**更隐蔽的方式**：
```
修改总价：total_price: 999 → 1
利用折扣：discount: 10% → 100%
篡改运费：shipping: 20 → -500（负数变成返现？）
```

**为什么会发生**：
后端没有重新计算价格，信任了前端传来的值。

### 2. 优惠券叠加

**场景**：结算时可以使用优惠券，前端限制只能选一张。

**关键思路**：
```
1. 前端限制 ≠ 后端限制
2. 观察请求数据结构 — 是否使用数组传递优惠券？
3. 后端是否对数组做了去重/数量限制？
4. 同一张券能否重复出现在数组中？
```

**攻击场景**：
```http
# 前端正常提交（单张优惠券）
POST /pay {"couponCodes": ["SAVE50"]}

# 攻击：传入多张/重复券
POST /pay {"couponCodes": ["SAVE50", "SAVE50", "SAVE50", ...]}
```

**核心问题**：后端是否逐一累加折扣而不做总量校验？

---

### 3. 流程跳过

**正常流程**：
```
步骤1: 选择商品 → 步骤2: 支付 → 步骤3: 确认订单
```

**攻击方式**：
```
直接调用步骤3的接口，跳过支付
前提：后端不校验每一步的前置条件
```

**关键思路**：
```
1. 每一步是否调用不同的 API 接口？
2. 后端是否独立验证前置步骤的完成状态？
3. 前端的流程控制（向导、按钮禁用）只是障眼法
```

---

### 4. 前端限制 vs 后端限制

**永恒的教训**：前端的任何限制都可以被绕过。

**常见"假限制"**：
```javascript
// 前端单选 → 实际请求是数组
body: JSON.stringify({ codes: [selectedCode] })

// 前端禁用按钮 → 直接调用接口即可
btn.disabled = true;

// 前端验证金额 → 拦截修改请求体
if (amount >= minPrice) { submit(); }
```

**攻击方式**：
```
1. 用 DevTools 观察请求结构
2. 用 Burp Suite / curl 直接构造请求
3. 修改请求参数突破前端限制
```

---

### 5. 通用攻击思路

**观察**：
```
- 请求中有哪些参数是可控的？
- 数据结构是什么？（对象 / 数组 / 嵌套）
- 正常操作和异常操作的响应有什么区别？
```

**测试**：
```
- 修改金额（0、负数、极大值）
- 重复提交（同一操作多次调用）
- 跳步执行（直接调用后续接口）
- 数组注入（单元素变多元素）
```

**验证**：
```
- 服务端是否真正校验了每个参数？
- 业务规则是否在服务端强制执行？
- 前端限制是否只是 UI 层面的？
```

---

### 6. 防御原则

1. **服务端验证一切** — 所有价格、折扣、状态都在后端计算和校验
2. **流程完整性** — 每一步接口独立验证前置条件是否满足
3. **幂等性设计** — 防止重复提交带来的累加效果
4. **输入去重** — 数组参数需校验重复元素
5. **总量校验** — 即使允许叠加，也要限制总折扣不超过原价
